JMeter 性能测试 · 关联：接口之间的数据传递

发表于 2026-07-14 更新于 2026-09-30 分类于 自动化测试 阅读次数：

前面几课都是独立的接口请求。但真实的业务是一串链路的：

每一步的输入，都来自上一步的输出。这就是关联。

一、什么是关联

关联就是”把上一个请求的返回值掏出来，喂给下一个请求”。

为什么需要它

HTTP 是无状态的。在真实项目中，很多动态数据无法写死：

场景 动态值 例子
登录后拿 token session_id / token 每次登录都不同
创建订单后查详情 order_id 服务端生成
列表页点进详情 帖子/商品 ID 列表返回
分页翻页 下一页的 URL 响应中返回

这些值不能硬编码，只能从响应里提取。

关联 vs 参数化

参数化 关联
数据来源 外部（CSV / 函数 / 变量） 上一个请求的响应
数据特点 预先准备好 运行时动态生成
典型工具 CSV Data Set Config 正则 / JSON 提取器
本质 输入驱动 输出驱动输入

实际项目两者都会用：
用 CSV 参数化提供测试账号 → 用关联提取登录返回的 token → 后续请求带着 token 发。

单独用任何一个都不够。参数化解决”用什么数据测”，关联解决”怎么串起来测”。

二、三种提取器

1. 正则表达式提取器（Regex Extractor）

最通用，适合非结构化响应或格式不规范的场景。

核心参数：

参数 说明
Apply to（scope） 搜索范围：body / headers / URL / response_code 等
Reference Name 变量名，后续用 ${变量名} 引用
Regular Expression 正则表达式，括号 () 是捕获组
Template 模板，$1$=第 1 组，$2$=第 2 组
Match No. 0=随机，正数=第 N 次匹配，-1=全部
Default Value 匹配失败时的默认值

💡 **Default Value 建议设成 NOT_FOUND**，不要留空。
留空的话，匹配失败时变量是空字符串，后续请求会带着空值发出去，报错信息很含糊。
设成 NOT_FOUND 就能一眼看出”是提取失败，不是接口失败”。

Match No. 详解：

值 含义 生成变量 适用场景
1 第 1 次匹配 ${refname} 只要第一个结果
2, 3, … 第 N 次匹配 ${refname} 指定位置
0 随机 ${refname} 模拟随机点击
-1 所有匹配 ${refname}_1, ${refname}_2, …, ${refname}_matchNr 遍历所有结果

-1 是个很实用的功能：一次提取所有匹配项，配合 ${refname}_matchNr 拿到总数，可以做”遍历列表全部元素”的测试。

2. JSON 提取器（JSON Extractor）⭐ 推荐

JSON 接口优先用这个，不要用正则。

问题 正则方案 JSONPath 方案
字段位置/换行变化 容易失效 按路径定位，稳定
多层嵌套 正则难写 用 $ 路径层级轻松穿透
数组提取 要写循环 $[*].field 一行搞定
可读性 差 好

核心参数：

常用 JSONPath 语法：

表达式 含义 示例
$ 根对象 整个响应
$.id 取对象中的 id 字段 {"id":1} → 1
$[0] 取数组第 1 个元素 [{"id":1},...] → {"id":1}
$[0].id 取数组第 1 个元素的 id → 1
$[*].email 取数组所有元素的 email [a,b,c]
$..name 递归取所有 name 字段 所有层级
$[?(@.id==1)] 条件过滤 取 id=1 的对象
$[0:3] 切片取前 3 个 索引 0,1,2

$[?(@.id==1)] 这个条件过滤很有用：从列表里按条件挑出目标对象，不用先算位置。

$..name 的递归搜索也值得记 —— 响应层级太深、不想数路径时，直接递归找。

⚠️ 注意：JSON Extractor 用 match_no=-1 时，会生成 var_1, var_2, … 和 var_matchNr，和正则提取器行为一致。

3. 边界提取器（Boundary Extractor）

最简单的方案：给定左边界和右边界，抠出中间的内容。

适用场景：响应格式固定、内容位置明确、不想写正则的时候。

比如响应里有：

  • 左边界：value="
  • 右边界：">

优势：不看正则语法的人也能维护。

劣势：只要响应格式有一点变化就失效，而且提取多个匹配项的能力不如前两者。

三、多级关联实战

链路设计：

关键点：

  1. 每一步都要断言，不能只看最后一步
    → 如果第 ③ 步提取失败，第 ④ 步的错误信息会误导你以为是用道具的问题

  2. 提取失败要能识别
    → Default Value 设成 NOT_FOUND，一眼看出是”提取失败”

  3. 中间任何一步挂了，整条链路都断了
    → 但报告里要能看出是哪一步，这就是为什么每步都要断言

四、正则方案 vs JSON 方案怎么选

情况 选哪个
响应是标准 JSON JSON 提取器
响应是 HTML / XML / 文本 正则提取器
格式极简单、左右边界明确 边界提取器
响应格式不规范、字段可能缺失 正则（但要写宽松一点）

一句话原则：能用 JSONPath 就别用正则。

正则依赖字符位置和格式，JSONPath 依赖结构。结构比格式稳定得多——接口多返回一个空格，正则可能就失效了，而 JSONPath 毫不知情地继续工作。

五、小结

要点 内容
关联本质 把上一个请求的返回值掏出来，喂给下一个请求
关联 vs 参数化 关联=输出驱动输入；参数化=输入驱动
正则提取器 通用；Match No. 支持随机(0)/指定(N)/全部(-1)
JSON 提取器 ⭐ JSON 接口首选；JSONPath 语法强大
边界提取器 简单但脆弱，格式一变就失效
实践建议 Default Value 设 NOT_FOUND；每步都要断言

本课要点：关联是输出驱动输入｜JSONPath 优于正则｜提取失败要能一眼识别｜每步都要断言
