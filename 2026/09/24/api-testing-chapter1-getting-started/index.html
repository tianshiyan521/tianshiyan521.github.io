接口测试实战 · 第1课：先跑起来，别管理论

发表于 2026-09-24 更新于 2026-09-30 分类于 自动化测试 阅读次数：

接口测试最大的问题是开头太抽象。

一上来就讲 HTTP 协议、状态码、请求方法、RESTful 规范……听的人云里雾里，动手的时候还是不知道该怎么下手。

这个系列反过来：先动手把请求发出去，看到响应了，再回头讲原理。

一、接口测试到底在测什么

你平时测游戏，点一个「领取」按钮，客户端偷偷发了一包数据给服务器，服务器回了一包数据。

接口测试 = 不点按钮，直接跟服务器对话，看它回得对不对。

就这么简单。所有方法论都是围绕这句话展开的细节。

三、★ 最重要的一个认知：HTTP 200 ≠ 用例通过

这是新人最容易踩、也最致命的坑。

看这个响应：

HTTP 状态码是 200，但这次请求彻底失败了。

游戏服务端的网关尤其如此——很多游戏网关的 HTTP 状态码永远是 200，真实成败藏在响应体里。

所以：

校验必须分四层

层 验什么 例子
协议层 HTTP 状态码 200 / 401 / 500
业务层 响应体业务码 code == 0
数据层 字段值与格式 data.level == 12、关键字段非空、类型正确
副作用层 数据库/下游真的变了 查库确认金币真的扣了、道具真的发了

缺任何一层都可能漏 BUG。 特别是第四层——接口返回成功但数据没落库，是最典型的”看着没问题其实是事故”。

四、一个接口的五大测试维度

设计用例时沿这五条线展开，就不会漏：

# 维度 具体校验点
1 功能正确性 正常入参返回预期结果、字段值准确、数据真的落库
2 参数校验 必填缺失、类型错误、长度边界、特殊字符、多余字段
3 业务逻辑 状态流转合法性、接口依赖串联、幂等性、并发一致性
4 异常与容错 错误码语义区分、超时重试、服务降级、重复提交
5 安全与权限 鉴权失效、水平/越权、注入、敏感信息泄露

关键概念：幂等性

同一个请求发两次，结果应该一致（或者第二次被正确拒绝）。

最典型的场景：领奖接口。

  • 第一次领 → 成功，金币 +1000
  • 第二次领 → 应该报错「已经领过了」，而不是再 +1000

如果没做幂等，玩家连点两下就能刷奖励。这是游戏里最常见的高危漏洞。

五、7 个任务：把接口测试走一遍

用一个练习台把上面这些概念跑一遍（自带假服务端，双击 练习台.html 就能玩，断网也行）：

# 做什么 你会看到
1 点「登录」 返回一个 token，相当于通行证
2 点「查角色信息」 当前等级 5、金币 1000
3 领「新手礼包」 成功，金币变 1100
4 再领一次新手礼包 报错 50003 已经领过了 ← 幂等性
5 领「王者礼包」 报错 50002 等级不足（要 10 级）← 边界值
6 用 GM 工具把等级改成 20，再领 这次成功了 ← 状态变更后的流程
7 把 token 改成 wrong，随便发个请求 报错 10002 token 无效 ← 鉴权

做完这 7 件事，你已经学会了 4 个核心概念：

  1. 接口 = 网址 + 参数 → JSON
  2. HTTP 200 ≠ 成功（每次报错 HTTP 码都是 200）
  3. 同一接口换参数就是另一条用例（任务 3 和 5 打的是同一个接口，只有 rewardId 不同）
  4. token 是通行证（任务 7 在测鉴权）

用例就是这么”设计”出来的 —— 把参数取遍所有可能的值。不是靠灵感，是靠方法。

六、为什么接口测试比 UI 测试更值得投入

接口测试 UI 测试
时机 后端交付即可测，不用等前端 必须等界面完成
速度 单接口 100ms 级 单用例 30s 级
稳定性 业务逻辑变了才挂 改个按钮挂一片
覆盖度 能打异常分支、越权、边界 只能覆盖用户点得到的路径

测试金字塔的占比：接口测试 **6070%**，单元测试 2030%，UI 测试 **10%**。

这个比例不是拍脑袋定的——越靠下的层，执行越快、越稳定、覆盖越广。把精力堆在 UI 层是性价比最低的做法。

七、完整工作流

第 ① 步往往是最大的门槛。 很多公司没有接口文档，或者文档早就过期了。这就需要”抓包反推”——后面第 3 课会讲一个极端案例：没有文档、没有抓包工具，怎么把一个私有协议的接口全扒出来。
