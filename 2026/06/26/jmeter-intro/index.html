JMeter 性能测试

发表于 2026-06-26 更新于 2026-09-30 分类于 自动化测试 阅读次数：

性能测试是测试工程师的能力分水岭。

功能测试能靠细心补，但性能测试必须靠工具 + 方法——而且它有一套自己独立的指标体系，不懂就会得出错误结论。

JMeter 是 Apache 开源的纯 Java 性能测试工具，是上手成本最低的选择。

为什么测试要学性能测试

三个实际理由：

① 接口”慢”是一个高频 bug

玩家反馈”点了半天没反应”，你如果只会说”我这边挺快的”，就没法推动修复。有了 JMeter 和性能指标，你才能说：**”这个接口 90% 请求响应超过 1.5 秒，超出 SLA 的 500ms 三倍。”**

② 并发问题是手动测试测不出来的

超卖、数据覆盖、重复领奖 —— 这些 bug 必须构造并发请求才能复现。JMeter 是最方便的手段。

③ 性能测试有自己独立的认知陷阱

比如：平均值会骗人。100 个请求里 95 个 100ms、5 个 8000ms，平均只有 495ms，看起来还行——但其实有 5% 的用户等了 8 秒。

不懂这些，你会用错误的数据得出”性能没问题”的结论。

专栏结构

这个系列按 7 天的学习过程整理成 5 篇：

篇目 内容 关键认知
入门 架构与第一个测试计划 GUI 写脚本，CLI 跑压测
监听器与结果分析 6 种监听器 + 实测数据 错误率必须追查来源
断言 5 种断言类型 采样器成功 ≠ 业务成功
参数化 CSV + 内置函数 硬编码的压测是假的
关联 正则 / JSON / 边界提取器 输出驱动输入

三个最重要的认知

① GUI 写脚本，CLI 跑压测

GUI 本身要渲染界面、绘制图表，这些开销会和被测系统抢 CPU 和内存。

我一开始不以为然，直到有一次在 GUI 里跑 50 并发，本机 CPU 直接拉满、界面卡住。
换成 CLI 跑，同样的脚本轻松跑到 200 并发。

工具自己成了瓶颈，这是性能测试里最讽刺的失误。

② 平均值会骗人，看分位数

性能 SLA 通常写”90% 请求响应时间 < 500ms“，而不是”平均响应时间 < 500ms”。

因为平均值会把少数极端慢的请求”平均掉”，掩盖真实的长尾体验。

看 90% Line / 95% Line / 99% Line，不要只看 Average。

③ 没有断言的压测只是在”发请求”

极端情况：被测服务挂了，返回一个静态错误页，HTTP 200，内容写着”系统维护中”。

没有断言的话，你的报告是全绿的。

采样器成功（请求完成了）≠ 业务成功（响应内容正确）。

适合人群：想入门性能测试 / 需要构造并发场景的测试工程师。
